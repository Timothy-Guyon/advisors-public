# Words: what is it called, and what does the code say?

The claims about names, and about what the code says beyond its names.

## Ubiquitous language

**The glossary's words are the code's words, and technical words extend them, never replace them.** A term means the same thing in a conversation, in the glossary and in a name in code, and when the word shifts, the code shifts with it. A word the glossary lacks goes into code only as a candidate, on the founder's word, and the session names it as missing; when the founder coins it through the writer (`python3 product.py coin`), the code follows the coined word, renamed if it differs. A store's, a framework's or a pattern's word extends the language where it names a technical thing, and is a second vocabulary where it names a thing the glossary already names; a second vocabulary is where the model splits without anyone noticing, and a model the people who know the domain cannot read is wrong in the model, not in them. Check: do the names in this change match the glossary, is every missing one named as a candidate, and does any name say in a technical word what the glossary says in its own? Sources: Evans, chapter 2, Communication and the Use of Language, including One Team, One Language; Fowler, Ubiquitous Language; Ousterhout, chapter 14, Choosing Names (14.4 Use names consistently).

## A borrowed name keeps its meaning

**A name taken from a pattern or from the domain's literature names in the model the concept its source names, and when the model's thing drifts from that concept the name changes or the word goes, never kept with a bent meaning.** A borrowed word brings understanding with it, the source's reasoning and what every reader who knows the source expects, and a word kept while the thing beneath it drifts misleads them all. So a pattern is a seed: its form is changed freely, its concept kept intact, and a word that does not fit is dropped before the code holds it. Check: does any name in this change come from a pattern or a text, does the thing it names still mean what the source means by it, and where the thing has moved, has the name moved with it? Source: Evans, chapter 11, Applying Analysis Patterns (Example: Earning Interest with Accounts, the dialog; Continuing Example: Insight into the Nightly Batch, the dialog; Analysis Patterns Are Knowledge to Draw On).

## Named for the effect, not the means

**A public name, of a type, an operation or an argument, says what it does for its caller and never how, and is chosen from the caller's side.** A name that tells the mechanism makes a reader open the body to use the thing, which is what the body was hiding; a name that tells the effect lets client code read as sentences of the model, and a reader who infers a purpose from a body may infer one it meets by chance. In a domain interface a rule is stated and not its enforcement, an action and not its steps. The name is chosen by writing the call before the thing, as a test or as the caller's line, so it is read from where it is used. Check: does every public name in this change say its effect without its means, and was the call written before the body? Source: Evans, chapter 10, Supple Design (Intention-Revealing Interfaces; Example Refactoring: Paint Mixing Application).

## A precise name

**A name read alone, away from its declaration and its uses, lets a reader guess closely what it refers to and what it does not.** A name that is only close enough, broad enough to fit many things, as count, result or status, is the Vague Name red flag: the reader supplies the meaning they expect and a wrong use reads as right, as one name for two kinds of block number once hid a bug for six months. A name says in a few words what matters most about the thing, claims no more than the thing is, and grows longer the farther its uses sit from its declaration. Where no short, precise name comes, the Hard to Pick Name red flag, the thing named is likely several things in one, and the fix is to cut it differently rather than to lengthen the name. Check: read alone, does each new name in this change say what it holds and what it does not, could any of them fit two things, and was any hard to pick? Source: Ousterhout, chapter 14, Choosing Names (14.1 Example: bad names cause bugs; 14.2 Create an image; 14.3 Names should be precise; 14.5 A different opinion: Go style guide).

## Named for its structure

**A piece of a screen that shows what it is given is named for its structure, never for the screen it was first placed on or the content it was first made to show.** A name taken from a place or from content, a home header or an item card, ties the piece to that place and that content, so the next use either copies it under a new name or bends it under a wrong one; named for its structure, a card, a row, a field, it holds any content of that shape. The piece that fills a display piece with a thing of the model is named for that thing in the glossary's words, so the content's name and the structure's name each say what their own piece is. Check: does any piece of a screen in this change take its name from the screen it sits on or from the content it shows, where it could hold other content of the same shape? Sources: Brad Frost, Atomic Design (2016), chapter 5, Maintaining Design Systems (Make it context-agnostic), `reference/atomic-design/chapter-5.md`; chapter 4, The Atomic Workflow (Establishing direction, Establishing content and display patterns), `reference/atomic-design/chapter-4.md`.

## The same way everywhere

**The same kind of thing is done the same way everywhere.** A name, a layout, an interface or a pattern, once chosen, is reused for every case of its kind, so a reader who has seen one can predict the next, and a second way is a decision, never a drift. Comments follow one convention too, what gets one and in what form, the form the language's documentation tool reads where there is one. For a name, that means one name for each recurring thing, used for it everywhere and for nothing else, with its purpose narrow enough that everything under the name behaves alike. The converse holds as firmly: a thing that differs is done differently, never forced into the familiar name or pattern, so that what looks like one kind of thing always is one. A better idea alone does not earn a second way: a convention gives way only to information not known when it was chosen, and only when every old use moves over, so none of the old way is left. A convention not written down is not followed, so one that spans the code is written where every reader is sent, and a local one, such as an invariant, beside the code it governs. Pieces of a screen are held to it too: one piece for each kind of element, a button, a field, a heading, under one name, and a near copy that differs from it by a detail nobody decided is a second way, brought back to the one or made a variation of it. Check: was a like case looked for in the code before this change chose its way, does the change follow it or add a second way, and does it give one name or one way to two things that differ? Sources: Ousterhout, chapter 17, Consistency (17.1 Examples of consistency; 17.2 Ensuring consistency; 17.3 Taking it too far); chapter 14, Choosing Names (14.4 Use names consistently); chapter 13, Comments Should Describe Things that Aren't Obvious from the Code (13.1 Pick conventions); Brad Frost, Atomic Design (2016), chapter 4, The Atomic Workflow (Show, don't tell: the power of interface inventories), `reference/atomic-design/chapter-4.md`; chapter 1, Designing Systems (Style guide benefits, Consistently awesome; A shared vocabulary), `reference/atomic-design/chapter-1.md`.

## Obvious to the reader

**Code is designed for ease of reading, not ease of writing, so that a reader's quick first guess at what it does is right.** A generic container, a pair or a tuple whose parts carry no names, is quick to write and leaves every reader to guess what its parts mean, where a small type of its own would name them. Code that cannot be understood at a quick reading is the Nonobvious Code red flag: its reader lacks some information, which is best made unneeded by abstraction and fewer special cases, next taken from conventions the reader already knows, and only then given at the spot in names and comments. Whether code is obvious is the reader's call, not the writer's, so a reviewer who finds it unclear is right however clear it looks to the one who wrote it. Check: would a quick reader's first guess at each part of this change be right, does a generic container stand where a named type would say more, and where code does what a reader would not expect, is that said where the reader will look? Sources: Ousterhout, chapter 18, Code Should Be Obvious (18.1 Things that make code more obvious; 18.2 Things that make code less obvious; 18.3 Conclusion); chapter 13, Comments Should Describe Things that Aren't Obvious from the Code (13.8 Conclusion); chapter 14, Choosing Names (14.5 A different opinion: Go style guide); chapter 1, Introduction (1.1 How to use this book); chapter 2, The Nature of Complexity (2.1 Complexity defined).

## What the code cannot say

**A comment says what the names and the types cannot, and a diagram or a document aims for the same.** A comment that repeats the code is noise; one that gives the why, what a caller may assume, or what is invisible in the types is worth writing, and it is written with the interface, not after. Everything else in the code is obvious without one. A diagram or a document is held to the same aim rather than to a rule: a diagram does best sketching the few things at the centre of one question rather than the whole model, a lasting document does best explaining meaning and pointing at the code rather than restating it, and when the words have moved on, a document is redrawn or archived rather than kept current by will. An interface is used from its declaration and what is said above it, never from its body: where the name and the types leave a caller guessing what a result means or what happens at the edges of an argument, a comment says so in the caller's terms and says nothing of how the body works, since one that does is the red flag Implementation Documentation Contaminates Interface. A comment on a declaration says what the thing is, not how the code changes it, and adds the precision its name and type lack: its units, whether its bounds are inclusive, what an absent value means. A comment sits as near as it can to the code it describes, at the narrowest scope that holds what it speaks of, and the farther it sits the more abstract it is, since a distant or detailed comment is the one left stale when the code changes. What a later reader of the code will need, such as the subtle problem that made a line the way it is, is written in the code and not only in a commit message, which a reader of the code rarely opens. Where the flow of control is hidden, as in a handler that something else calls, the handler's comment says when it is called. A thing that needs a long explanation to be used safely is a sign its design is not right, and the first fix is a simpler design rather than more words. Check: could a reader write any comment in this change from the code beside it (Comment Repeats Code), is every comment beside the changed code still true, can each new interface be used without reading its body, and does a document or diagram it touches restate the code or speak words the code no longer does? Sources: Ousterhout, chapter 13, Comments Should Describe Things that Aren't Obvious from the Code (13.3 Lower-level comments add precision; 13.5 Interface documentation; 13.6 Implementation comments: what and why, not how); chapter 15, Write the Comments First; chapter 16, Modifying Existing Code (16.2 Maintaining comments: keep the comments near the code; 16.3 Comments belong in the code, not the commit log; 16.5 Maintaining comments: check the diffs; 16.6 Higher-level comments are easier to maintain); chapter 18, Code Should Be Obvious (18.2 Things that make code less obvious); Evans, chapter 2, Communication and the Use of Language, Documents and Diagrams; Ousterhout, chapter 12, Why Write Comments? The Four Excuses (12.1 Good code is self-documenting); chapter 2, The Nature of Complexity (2.3 Causes of complexity).

## The core is marked

**Where the model lives, a reader can tell at once what is in the core domain and what is not, and a change that moves that line says so.** Left in heads, the core is chosen differently by each reader and by the same reader on different days, and the sifting costs every change; the mark is whatever lets a reader see in or out without thought, a module, a comment, a heading, with no attempt to explain the role. A change that leaves the line where it is is an ordinary change; one that moves it, by altering a core thing's relations or by bringing a thing into the core or out of it, is named as such in its spec. Check: can a reader of this change tell, without sifting, whether each thing it touches is in the core, and if it moves the core's line, does the spec say so? Source: Evans, chapter 15, Distillation (Highlighted Core: Flagged Core; Distillation Document as Process Tool).
