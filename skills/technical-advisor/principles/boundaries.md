# Boundaries: where does it live, and what does it hide?

The claims about modules, layers and the borders between contexts.

## Deep modules

**A module hides a lot behind a little.** A good module has a small interface and a large implementation behind it; a shallow one has an interface as large as its insides and hides nothing. Fewer, deeper modules beat many thin ones. An interface is everything a caller must know to use the module, its signatures and the rules no signature states, an order of calls or an effect beyond the return, and depth is measured against all of it. An abstraction fails two ways: it shows a detail no caller needs, which adds to what each must know, or it hides one a caller does need, a false abstraction in Ousterhout's word, which looks simple and is not. What a module hides is a design decision, a format, a representation, an algorithm or an assumption, and a field kept private but handed out through a getter and a setter is not hidden. Its interface speaks in other terms than its representation: a module that hands out its internal collection, or whose operations mirror how it stores things, makes its callers change whenever its storage does. A module is deep when it can be described both briefly and completely; one whose description must tell how it works before it can be used is shallow, and one that cannot be described briefly is the red flag Hard to Describe. Check: is this one deep module with a small interface, or a shallow pile that leaks its insides (Shallow Module), does its interface return or mirror its representation or hide a detail its callers need, and can it be described briefly and completely (Hard to Describe)? Sources: Ousterhout, chapter 4, Modules Should Be Deep (4.2 What's in an interface?; 4.3 Abstractions; 4.4 Deep modules); chapter 9, Better Together or Better Apart? (the opening; 9.2 Bring together if it will simplify the interface); chapter 5, Information Hiding (and Leakage) (5.9 Taking it too far); chapter 6, General-Purpose Modules Are Deeper (6.4 Generality leads to better information hiding); chapter 7, Different Layer, Different Abstraction (7.4 Interface versus implementation); chapter 19, Software Trends (19.6 Getters and setters); chapter 13, Comments Should Describe Things that Aren't Obvious from the Code (13.5 Interface documentation); chapter 15, Write the Comments First (15.3 Comments are a design tool).

## Split where each part reads alone

**A piece of code is split only where each part can then be read without the other, and never for its length alone.** A split adds an interface and puts related lines apart, so it pays only when the whole gets simpler: a subtask is drawn out where the child can be read without the parent and the parent without the child's insides, and one function becomes two only where its interface did unrelated things and most callers then need just one of the two. Splitting by size alone is classitis, in Ousterhout's word: each piece comes out simple and the whole grows more complex by every interface added, so a long function that does one thing completely behind a simple signature is deep and stays whole. Two pieces are joined where they share knowledge, where each is used whenever the other is, or where one cannot be understood without the other, the last the red flag Conjoined Methods, and joined they can often drop the interface that ran between them. Check: can each part this change splits off be read alone, would a reader flip between any two pieces to follow either (Conjoined Methods), and is any split made for length alone? Sources: Ousterhout, chapter 4, Modules Should Be Deep (4.5 Shallow modules; 4.6 Classitis); chapter 9, Better Together or Better Apart? (9.1 Bring together if information is shared; 9.2 Bring together if it will simplify the interface; 9.6 Example: separate class for logging; 9.8 Splitting and joining methods).

## Pull complexity downward

**The implementer carries the weight, not every caller.** When something has to be complicated, it is better for the one implementation to carry it than for every caller to carry a share; a simple interface matters more than a simple implementation. Complexity is weighed by how often work passes through it, so a complicated part that no change needs to open costs little, and hiding it there is nearly as good as removing it. A configuration parameter, like an exception thrown because a case was hard, hands the problem to every caller, so before one is exported the question is whether a caller could choose a better value than the module can work out. Where the module can know the right value and a caller must only sometimes differ, the module supplies it as a default, so the common case names nothing and only the rare caller learns the option exists. Complexity is pulled down only where it belongs with what the module already does, spares many callers and makes the interface simpler; a caller's own concept pulled into a lower module is information leakage, not depth. Check: does this change push onto callers a case or a setting the module could absorb, does the common case make a caller learn a rarely used one (Overexposure), and does whatever is pulled down belong with what the module already does? Sources: Ousterhout, chapter 8, Pull Complexity Downwards (8.2 Example: configuration parameters; 8.3 Taking it too far); chapter 2, The Nature of Complexity (2.1 Complexity defined); chapter 5, Information Hiding (and Leakage) (5.7 Example: defaults in HTTP responses); chapter 4, Modules Should Be Deep (4.7 Examples: Java and Unix I/O).

## The hard part stands alone

**The most intricate computation in a change goes into a thing that depends on nothing of the model but primitives, so it can be read and tested alone.** Every type a thing refers to, in its fields, its arguments or its returns, is one more thing to hold in mind while reading it, and a primitive that stands for a concept is a dependency too, only a hidden one. A dependency is kept when it is part of what the thing means and cut otherwise; the ordinary way to cut is to make the computation an immutable value held by the more connected thing and pointed at one way. Cutting dependencies never means reducing a thing to bare primitives; the concept stays, its ties go. Check: for the hardest computation in this change, what does it depend on beyond primitives, and is each dependency part of what it means? Source: Evans, chapter 10, Supple Design (Standalone Classes).

## Cohesive mechanism

**An intricate computation that the model poses and a studied formalism solves is a cohesive mechanism: a part of its own, named in the formalism's words, holding no concept of the domain, that the model's things call through an interface that says what and never how.** The expressive model states a fact, a rule or a problem, and the mechanism resolves it; mixed together, the how swamps the what, and the operations that solve the problem bury the ones that state it. The first move is a model that makes the computation simple, and the mechanism is cut only when what remains is still intricate and coherent on its own, a walk over a graph, the combining of specifications, a formalism with a literature that can be looked up rather than worked out by trial; it is cut to the subset the model needs and never to the formalism's full generality, and its separate home may later fold back into the thing that uses it so long as the declarative interface stays. A mechanism that is itself the app's distinctive value is the one exception, and it stays in the core. Check: does the hardest computation in this change state the problem or solve it, is any solving mixed into a thing that should only state, is the mechanism named in its formalism's words with no concept of the domain inside it, and does its caller read as a statement? Source: Evans, chapter 15, Distillation (Cohesive Mechanisms; A Mechanism in an Organization Chart; Generic Subdomain vs. Cohesive Mechanism; When a Mechanism Is Part of the Core Domain; Full Circle: Organization Chart Reabsorbs Its Mechanism; Distilling to a Declarative Style).

## Somewhat general

**One general interface beats a branch per caller.** An interface that handles the general case one way is simpler than one with a special case for each caller anyone can think of today, and deeper for it. Somewhat general means the module's functionality reflects today's needs and its interface does not: the interface is general enough for more than one use, and never so general that today's use is hard. A special-purpose interface leaks: the caller's concepts appear in the module beneath it, and each new feature above needs a new method below, so the two can no longer change apart. A general mechanism holds no code for one of its uses: that code lives in the module that has the use, and the policy for combining uses lives with the caller above, so none of the three must know the others; a mechanism that mixes them is the red flag Special-General Mixture, since each change to a use then reaches into the mechanism. Check: does this interface handle the general case, or carry a branch or a method per caller, is it the simplest interface that covers every current need, and is it still easy to use for the need at hand? Sources: Ousterhout, chapter 6, General-Purpose Modules Are Deeper (6.1 Make classes somewhat general-purpose; 6.2 Example: storing text for an editor; 6.5 Questions to ask yourself); chapter 9, Better Together or Better Apart? (9.4 Separate general-purpose and special-purpose code; 9.7 Example: editor undo mechanism).

## Different layer, different abstraction

**Each layer offers a different abstraction from the layers beside it, and an element that adds interface without taking complexity off its callers is left out.** Every function, argument, type or wrapper is one more thing to learn, so it earns its place only by hiding something its callers would otherwise carry. A pass-through method, which only forwards its arguments to one with the same signature, and a pass-through variable, carried through functions that never read it, show two layers sharing one abstraction; the callers then call the lower thing directly, the work moves to one side, or the two merge, and the variable moves into an object both ends already hold. A shared signature is sound where each holder does distinct work, a dispatcher choosing among handlers or several implementations of one interface, and a wrapper that repeats the interface of what it wraps to add a little is a last resort, after adding the feature to the thing itself, to its one use, or to a part of its own. Check: does this change add a function that only forwards a call (Pass-Through Method), an argument carried through functions that never use it, or a wrapper whose interface repeats what it wraps, and what complexity does each new element take off its callers? Source: Ousterhout, chapter 7, Different Layer, Different Abstraction (7.1 Pass-through methods; 7.2 When is interface duplication OK?; 7.3 Decorators; 7.5 Pass-through variables; 7.6 Conclusion).

## Modules are concepts

**A module groups the things understood together, is named with a glossary word, and never splits one thing's data from its behaviour.** Modules are part of the model: a folder is a chapter of its story, named for a concept and not for a kind of code, so a reader told to look in one can think about its things together. A layout that puts a thing's data in one place and its rules in another robs the model of its cohesion, and modules move with the model, since the first cut is usually naive. A module cut by when its code runs, one part to read a thing, one to change it and one to write it back, is temporal decomposition, in Ousterhout's word: the same knowledge lands in each part, so modules are cut around the knowledge each task needs instead. Check: is each folder this change touches named for a concept in the glossary's words, does any split one thing's data from its behaviour by kind, and is any module it adds cut by the order its steps run in (Temporal Decomposition)? Sources: Evans, chapter 5, A Model Expressed in Software, Modules, and The Pitfalls of Infrastructure-Driven Packaging; Ousterhout, chapter 5, Information Hiding (and Leakage) (5.3 Temporal decomposition; 5.5 Example: too many classes).

## Components

**Components are built as Atomic Design describes.** Five levels, each made from the one below: atoms, the smallest pieces of an interface that still mean something on their own (a label, an input, a button); molecules, a few atoms working as a unit (a label, an input and a button as one search form); organisms, molecules and atoms composed into a distinct section (a header); templates, organisms laid out as a page's skeleton, content shown as placeholders; pages, a template with real content, where the design is judged. A new piece of a screen is placed at its level and built from the levels below it. A larger piece holds the smaller ones by including them, never by copying their insides, so a change to a smaller piece reaches every larger one built from it. Placing a piece at its level does not draw it into a definition or a file of its own; `CLAUDE.md` says when a piece is drawn out. Check: is each new piece of a screen placed at its level and built from the levels below, by including them rather than copying them? Sources: Brad Frost, Atomic Design (2016), chapter 2, Atomic Design Methodology, `reference/atomic-design/chapter-2.md`; chapter 3, Tools of the Trade (Building atomic design systems with Pattern Lab), `reference/atomic-design/chapter-3.md`; chapter 4, The Atomic Workflow (Rolling up our sleeves, In-browser iteration), `reference/atomic-design/chapter-4.md`. Accepted by the founder, 2026-10-13: a pattern the app implements and adheres to.

## A piece holds no data of its own

**A piece of a screen below the page takes what it shows as input and reads no data itself, so the page is the one level where the app's data meets its pieces.** Kept apart from its content, a piece holds anything of its shape, is changed once for every place it shows, and can be shown and tested alone with sample content; one that reaches for its own data is tied to the screen it was made for, and every change to that data reaches into it. Its layout is kept apart the same way: it fits the space it is placed in rather than assuming the screen around it, so it can be placed anywhere without change. The page hands each piece what it shows, or hands it the smaller piece already filled, so no level between carries data it never reads. Check: does any piece of a screen in this change, below the page, read the store or the model itself, hold content it could take as input, or assume the size or the screen it sits in? Sources: Brad Frost, Atomic Design (2016), chapter 3, Tools of the Trade (Working with dynamic data; Viewport tools for flexible patterns), `reference/atomic-design/chapter-3.md`; chapter 5, Maintaining Design Systems (Clearing technical hurdles, Bridging the markup gap with templating languages), `reference/atomic-design/chapter-5.md`; chapter 1, Designing Systems (Style guide benefits, Testing, testing, 1-2-3), `reference/atomic-design/chapter-1.md`.

## Variations are inputs to one piece

**A piece of a screen drawn into one definition takes each of its variations, a state, a kind or a range of content, as an input, never as a copy of itself.** A copy made for a variation drifts from the piece it came from, and a fix to one misses the other; as inputs, the variations are declared with the piece, so a reader sees every form it can take, and each can be shown alone by handing the piece that input. Which variations a piece needs is set by the content and the use it will meet, not by the case it was drawn with: nothing to show, one item and many, the longest text, a missing picture, and the states a control passes through, pressed, disabled and loading. Check: does this change copy a piece already drawn into one definition to make a variation of it, and does each piece it adds or changes take as inputs the states and the range of content it will meet, the empty, the one, the many and the longest, and is each input named for what it changes in the piece rather than for who asks? Sources: Brad Frost, Atomic Design (2016), chapter 3, Tools of the Trade (Articulating pattern variations with pseudo-patterns), `reference/atomic-design/chapter-3.md`; chapter 4, The Atomic Workflow ((Re)setting expectations, Death to the waterfall; Rolling up our sleeves, In-browser iteration), `reference/atomic-design/chapter-4.md`; Brad Frost, Atomic Design, the post of 2013 that named the method (Pages), `reference/atomic-design/atomic-web-design-2013.md`.

## Generic subdomain

**A part of the model that any app of its kind would hold is a generic subdomain: a module of its own, modelled from a published model where one exists, with no trace of this app's specialties in it and no generality beyond what this app needs.** Such a part is of the model and essential, a unit, a time, a person, an account, but it carries none of the knowledge that makes the app what it is; held apart, the core reads without its detail and the part can be understood without the core. Two cuts keep it: a thing specific to this app found inside it moves out, to the core or to a supporting part of its own, since it belongs with the specialised model and would have to be unpicked when the generic part grows; and the part is built only as far as the app's scenarios reach, never for reuse, since the model is the thing worth reusing and not the code. Check: does this change put a thing of this app's own domain into a part any app would hold, or widen such a part past what a scenario reaches, and where a published model exists, is it the one used? Source: Evans, chapter 15, Distillation (Generic Subdomains; Published design or published model; A Tale of Two Time Zones; Generic doesn't mean reusable).

## Cut at the domain's grain

**An operation, a type or a module is cut at the unit the people who know the domain would name, no finer and no coarser.** Cut finer, a caller must assemble pieces the domain never separates, and a concept can vanish between them; cut coarser, the unit mixes concepts, its interface cannot say all it does, and callers copy out the part they wanted. One act of the domain is one operation, which does not stop halfway and does not run on into the next act; what the app's user never takes apart stays one lump with no option to dissect it. A cut that suits the code as it stands but matches no sentence of the domain is an expedient, and a change that forces many cuts to move at once says the model is wrong, not the cuts. Check: is each unit this change adds or splits one thing a person of the domain would name, and is any cut here an expedient of the current code rather than a line of the domain? Source: Evans, chapter 10, Supple Design (Conceptual Contours; Example: Accruals; An Unanticipated Change).

## One place for each piece of knowledge

**Every piece of knowledge has one place, and every other place points there.** When two modules both know the same thing, the knowledge has leaked, and the second copy is where the bug hides; the fix is to move it to one place and delete the copy. This is about knowledge, not about lines that happen to look alike, and it holds for rules, principles and facts as much as for code. Knowledge can leak with no trace in an interface, as when one module writes a format and another reads it, and that back-door leakage is the harder to see. Leaked knowledge is cured by merging the modules where they are small and tied to it, or by a module of its own only where that module's interface is simpler than what it holds. Lines that look alike are still worth reading, since a nontrivial piece of code repeated nearly the same is the red flag Repetition, a sign that an abstraction has not been found; by the third use it is drawn into one place, where the repeated part is long and the call that replaces it takes a simple signature. Documentation is held to it as code is: a design decision is written once, where a reader of the code will look for it, and a call site, another module or a copy of an outside text points there rather than retelling it. Check: does this change state anything the code or a file already states, or let two modules depend on one format or decision (Information Leakage), and if so, which copy goes? Sources: Hunt and Thomas, topic 9, DRY; Ousterhout, chapter 5, Information Hiding (and Leakage) (5.2 Information leakage); the founder's rule, 2026-10-13; Ousterhout, chapter 9, Better Together or Better Apart? (9.1 Bring together if information is shared; 9.3 Bring together to eliminate duplication); chapter 16, Modifying Existing Code (16.4 Maintaining comments: avoid duplication).

## One change, one place

**Unrelated things stay unrelated, so one change touches one place.** Changing one part should not force a change in another; parts kept apart can be tested, replaced and understood alone, and a change that touches many places is the first symptom of complexity. Of complexity's three symptoms the worst is the unknown unknown, a place that must change with the others and that nothing in the code points to; a dependency that must exist is made obvious, run through one name the type checker follows, so every place it reaches can be found. Where a decision cannot be kept inside one module, the places it reaches are listed once, at the place a developer changing it reaches first, and the list is marked as a compromise, never taken for the shape. A piece of a screen reaches every larger piece and every page that includes it, so those are found from its name and listed before it is changed. Check: what does this touch? List the files and the callers before editing, and keep the list short; must anything change with them that nothing in the code points to? Sources: Hunt and Thomas, topic 10, Orthogonality; Ousterhout, chapter 2, The Nature of Complexity; chapter 13, Comments Should Describe Things that Aren't Obvious from the Code (13.7 Cross-module design decisions); Brad Frost, Atomic Design (2016), chapter 3, Tools of the Trade (Providing context with pattern lineage), `reference/atomic-design/chapter-3.md`; chapter 5, Maintaining Design Systems (Make it contextual), `reference/atomic-design/chapter-5.md`; chapter 1, Designing Systems (Style guide challenges, Lack of context), `reference/atomic-design/chapter-1.md`.

## Composed, not inherited

**Implementation shared between types is composed from a helper each one uses, not inherited from a parent whose state they share.** Inheriting an implementation spares the copies but ties the parent to every child: the state both reach leaks between them, so a change to the parent means reading every child and an override means reading the parent. A small helper each type builds on shares the code without the tie, and where a parent cannot be avoided, it alone writes its state and the children only read it or call its methods. Inheriting an interface alone is another thing, and a good one: an interface with many implementations holds only what they share, which makes it deeper. Check: does this change share implementation through a parent type where a helper could carry it, and where a parent stays, does any child write the parent's state? Source: Ousterhout, chapter 19, Software Trends (19.1 Object-oriented programming and inheritance).

## Infrastructure behind one boundary

**The domain knows nothing of its infrastructure or its screens, dependencies point one way, and every big choice sits behind one boundary and can change.** Domain code does not know about databases, HTTP, files or UI frameworks; infrastructure depends on the domain, never the other way round, and the domain's door to storage speaks the domain's language (find by, save, all). The parts stand in layers, screen, task, domain, infrastructure, and a part depends only on its own layer or the ones beneath: a domain thing does not draw itself, store itself or know what screen will show it, and where a lower part must tell an upper one something, it does so through an interface the lower part declares, never by reaching up. A framework is used for the technical problem it solves and not as a mould: a domain thing is a plain type that extends nothing of the framework's. A choice that may change, the store, the framework, the vendor, the host, is treated as if it will, and kept behind one boundary so that it can. A framework that constrains the core domain more than it saves is backed out of the core, or the core is redrawn to the part the framework does not touch. Check: is the domain part free of store, HTTP, screen and framework details, does anything in it extend a framework's type or reach up a layer, and is the thing that might change behind one boundary? Sources: Evans, chapter 4, Isolating the Domain (Layered Architecture, Relating the Layers, Architectural Frameworks); chapter 6, The Lifecycle of a Domain Object (Repositories); chapter 15, Distillation (Core Domain, Who Does the Work); Hunt and Thomas, topic 11, Reversibility; Fowler, Presentation Domain Data Layering; Ousterhout, chapter 7, Different Layer, Different Abstraction.

## A technical part is judged by the domain code that uses it

**A technical part of the app's own, a door to the store, an engine, a helper the domain code calls, is held to the same test as a framework from outside: it earns its place by what the domain code can say and change more easily through it, it is cut and recut from what its callers ask of it, and a caller that reaches around it is the sign the part is cut wrong, answered by recutting the part and never by forbidding the reach.** A framework or an in-house layer can bend the model's expression or make a change hard without ever meaning to touch the domain, so the sign is read in the domain code, a thing made mutable, flattened or renamed for the part's sake, and never in the part's stated scope. A part that is circumvented is no part, since the app then carries its cost and none of its boundary; so each bypass is folded into the part as what it should have offered, or the part gives up that ground, and what the part hides is detail no caller needs to decide, never a choice that is the caller's. Check: does any domain code in this change reach around a door, an engine or a helper the app holds for that purpose, and if so is the part recut to carry it; does any domain thing here bend its shape for a technical part that never set out to touch it; and does the part hide only what no caller needs to decide? Source: Evans, chapter 17, Bringing the Strategy Together (The Same Goes for the Technical Frameworks; Don't Write Frameworks for Dummies to Use; Assessment First).

## One door per root

**The store has one door per root that needs finding, the door behaves like a collection, and nothing else gets a door.** The door offers add, remove and finds asked in the domain's words, as if every thing of that kind were held in one collection in memory; a part or a value is reached from its root and never through a door of its own, and a value that seems to need finding is an entity not yet recognised. Whether a thing is reached by walking from another or by a find is a design decision made aloud, not a default. The door does not commit; the task that called it does. An in-memory stand-in for the door serves the tests. Check: does this change open a door to the store for anything but a root, reach a part by query, or commit inside the door? Source: Evans, chapter 6, The Lifecycle of a Domain Object (Repositories, Querying a Repository, Implementing a Repository).

## The store mirrors the model

**A store made for this app is shaped by the model, named the same, and written only through the model's rules.** Where the store exists only to hold the model's things, its shape and the model's do not diverge: one row holds a thing with its parts, a key points at another root, tables and columns carry the model's names and relations, so the mapping is read off by inspection and needs no table of its own. What the model holds as data, the store holds as data, never as structure: a thing the model defines by data gets no column of its own. Nothing writes the store around the rules the model enforces: a thing made whole by the model is written as it was made, never by a path that skips its rules. Check: does this change shape the store apart from the model, name a thing differently in the two, or write the store past the model's rules? Source: Evans, chapter 6, The Lifecycle of a Domain Object (Designing Objects for Relational Databases).

## The model in one place

**All the code that expresses the model sits in one place, so the model can be read as a whole.** Domain code spread through screens, stores and scripts cannot be seen as a system: a change to a screen changes a rule without anyone meaning it, and the model's shape cannot be judged because its parts are never seen together. Gathered in one place, the model's things can be read, checked and changed side by side; how small that place may be is the building rules' question, that there is one is this claim's. Check: does this change put model code anywhere but the model's place, so that the model can no longer be read whole? Source: Evans, chapter 4, Isolating the Domain, the opening and The Domain Layer is Where the Model Lives.

## Order evolves

**Where a thing goes is told by its folder's name until that stops working; only then is a rule laid over the whole domain part, the loosest that fixes what showed, named in the domain's words, with every exception flagged, and dropped when the exceptions pile up.** Such a rule over the whole, a set of strata every thing belongs to one of or a protocol every part follows, is a large-scale structure, in Evans's word. One imposed before the domain is understood freezes decisions that want detail in hand, and parts are dumbed down to fit it or built around it until there is no structure at all; one that fits pushes every part the same way and cuts the options a decision must weigh, so each rule of it must make a change easier and not only more uniform. The technical layers, screen, task, domain and infrastructure, are not this and stand regardless. Check: does this change impose a rule on parts it does not touch, and where the domain part already holds such a rule, does the change follow it, flag its exception, or show the rule should go? Source: Evans, chapter 16, Large-Scale Structure (Evolving Order; How Restrictive Should a Structure Be?; Refactoring Toward a Fitting Structure, Minimalism).

## The task holds no rule

**The code that drives a task says when, the domain says what, and infrastructure says how.** Between a screen and the model sits a thin part that runs a job for a user: it calls the model's things in order and asks infrastructure for what it needs. It holds no rule of the domain and no state of the domain's situation, only how far the job has got, and a rule found there is moved to the thing it belongs to. Check: does any function in this change that sequences a task hold a rule or a fact of the domain that belongs to a thing of the model? Source: Evans, chapter 4, Isolating the Domain, Layered Architecture, and the online banking example.

## One bounded context until the words part

**The app is one bounded context, one model unified end to end, and a second context is drawn only where the same word must mean two things or one part's specialised jargon would burden the rest, never for a kind of code or a convenience of the moment.** One coherent model is easier to hold than two with a mapping between them, a user's task flows better through one, translation between two can be hard and sometimes impossible, and two models that grow apart are hard to merge again; so the border is drawn on a logical inconsistency found between two parts, and not before. Within the one context every term has one meaning and no two rules contradict, and a part that must say a word differently is the sign the border is wanted there and nowhere else. Check: does this change draw a second context, and if so, which word must mean two things across the line, and what would it cost to unify the two instead? Source: Evans, chapter 14, Maintaining Model Integrity (the opening, on unification; Bounded Context; Choosing Your Model Context Strategy, Transforming the Boundaries; the closing paragraphs).

## Conformist, anticorruption layer or separate ways

**Where the app takes a model it does not control, it stands in one of three relations to it, chosen aloud: conformist, taking the outside model's words and shapes whole as its own; an anticorruption layer, keeping its own model with the translation at one door; or separate ways, no connection at all; and never a mix of the first two.** Conforming gives up the ideal model and is spared the whole of the translation, and is right where the app is an extension of the outside thing and that thing's model is sound and in a compatible style; the anticorruption layer is right where the app's own model is the thing being built, since a wide border left unguarded bends the model piece by piece toward the outside one; separate ways is right where the connection would cost more than it returns, which is the first question asked of any integration. The mix, a few outside words taken as ours beside a few translated at the door, is a bounded context nobody drew, where every reader must know which word came from where. Check: which of the three relations does this change take to each outside model it touches, is that said, and does any outside word enter the model as ours while others of the same model are translated at the door? Source: Evans, chapter 14, Maintaining Model Integrity (Conformist; Anticorruption Layer; Separate Ways; Choosing Your Model Context Strategy, Accepting That Which We Cannot Change and Relationships With the External Systems).

## A border between contexts

**A model is valid inside one context, a door to an outside system is named for what it does for us and not for what it talks to, and what comes through it arrives in our words.** The same word may mean different things in two contexts, which is fine as long as the border is drawn; where one context talks to another, or to an outside system, a thin translation sits at the border, and the outside system's shapes and names stop there. The translation runs both ways: what goes out through the door leaves in the outside system's words as what comes in arrives in ours, and the outside system is taken as it stands, with no change asked of it. The door is named for the responsibility it carries in our model and presented as a service with the machinery hidden beneath, so a reader reads our model and the system behind the door can be swapped without a name changing; the outside system's categories cross as things of our model, never as its strings, so a change out there ripples only as far as the door. Check: does anything in this change carry another context's, or an outside system's, shape past the border, is the door to an outside system named for our job rather than for the system, and does any of its categories cross as a raw string? Sources: Evans, chapter 7, Using the Language: An Extended Example (New Feature: Allocation Checking); chapter 14, Maintaining Model Integrity (Bounded Context, Anticorruption Layer and Implementing the Anticorruption Layer, Conformist, Separate Ways, Choosing Your Model Context Strategy); Fowler, Bounded Context.

## Published language

**What crosses a border between two contexts crosses in a published language, a documented form of its own that says the domain information both sides need, and neither side's internal types are the wire.** A model used as its own interchange form is frozen by every reader of it, since a change to the model breaks them all, and the model is the more complex and the less documented of the two things for the job; a language made for the crossing is small, named, written down beside the code, and translated into and out of on each side. Where an industry form exists it is used; otherwise the language is cut from the distilled core and no wider. Check: does anything in this change send a type of the model across a border as it is, and if a form crosses, is it documented as a language of its own? Source: Evans, chapter 14, Maintaining Model Integrity (Published Language; Transformations, Open Host Service to Published Language).

## Context map

**Where more than one model is in play, the implicit one in a script or a data file as much as the one in the domain part, each is named with its bounded context and the points where two touch are written down, with what crosses and whether it translates or shares, before any border is moved.** Without the map, a change in one model blurs the edge of another without anyone meaning it, and the connections bleed: one part's type grows a field for another part's purpose. The map names each context in the glossary's words, marks each contact point and says whether it translates or shares; what the terrain should look like is a separate question from what it is, taken up after the map is drawn. Check: does this change move a border, and if so, is every model in play named, and at each point where two meet is the translation or the sharing written where the next reader will find it? Source: Evans, chapter 14, Maintaining Model Integrity (Context Map; Shared Kernel; Choosing Your Model Context Strategy).
