# Errors: what happens when it is wrong?

The claims about wrong input and wrong state, in the order they are tried: first make the error impossible; where it must exist, name the contract; when the contract breaks, stop there.

## Define errors out of existence

**Shape the interface so the error case cannot happen.** An error that is raised must be handled everywhere it can reach; an interface shaped so the case does not arise needs no handling at all, and where an error must exist, it is handled in one place. Each error a module raises is part of its interface and makes the module shallower, and one raised because the right behaviour was unclear passes the question to a caller who knows less. The usual move is to restate what the operation promises as a state to reach rather than a step to take, so the case that was an error becomes a call whose work is already done. An error that must exist is masked low, inside the module that meets it, where every caller would do the same about it, or aggregated high, left to rise to one handler near the top that reports the message written where the error was raised. An error is defined away or masked only where no caller needs to know of it; one a caller must act on stays in the interface. Check: can this error be defined out of existence at the edge where data enters, instead of handled at runtime, and if it must exist, is it masked in the module that meets it or left to one handler near the top rather than caught at each call, and is any error hidden that a caller needs? Source: Ousterhout, chapter 10, Define Errors Out of Existence (10.2 Too many exceptions; 10.3 Define errors out of existence; 10.5 Example: Java substring method; 10.6 Mask exceptions; 10.7 Exception aggregation; 10.10 Taking it too far).

## Say what it needs and promises

**A function says what it needs, what it promises and what stays true; what the types cannot state, a test states; and a promise that would surprise the people who know the domain marks a missing concept.** A caller that breaks the contract is told so loudly and early, a reader can tell from the interface what may be assumed, and the types carry as much of the contract as they can. A promise or an invariant is written in terms of states and never of steps, so its test is the setup, the call and the check, and an invariant is stated for a cluster as well as for a type. When the true promise of an operation is one a person of the domain would not guess, the fix is neither a comment beside it nor a change that alters its argument to make the arithmetic come out, but a model in which the promise is obvious. What an interface says includes every effect a later call can see that is not in its result, every error that can leave it, and every precondition that remains, the fewer the better. Check: does the required check pass (`CLAUDE.md` names it), does each new interface say what it needs and promises, is each promise the types cannot carry written as a test, and would any promise in this change surprise the people who know the domain? Sources: Hunt and Thomas, topic 23, Design by Contract; Evans, chapter 10, Supple Design (Intention-Revealing Interfaces; Assertions; Example: Back to Paint Mixing); Ousterhout, chapter 13, Comments Should Describe Things that Aren't Obvious from the Code (13.5 Interface documentation).

## Crash early

**A program that notices it is wrong stops there.** A crash near the cause beats a wrong answer far from it, and a wrong answer that gets saved is the costliest kind, because it is read back later as the truth. An error that is rare and that the app could do nothing useful about, its memory gone or its own state found inconsistent, gets no handler of its own and ends with a message that says what happened, unless recovering from it is part of what the app is for. Where a recovery from a large failure must exist anyway, a rare small error is promoted to that failure, so one recovery path serves both and runs often enough to be trusted; a frequent error is not, since each promotion pays the large recovery's cost. The same holds where an error is handled: a handler that swallows a failure, reports success after one, or catches more than it was written for gives the wrong answer far from the cause, so a failure travels until it reaches the code that can act on it, and what a caller gets back, its result and its declared errors, lets it tell every failure apart from success. Check: when this code finds itself wrong, does it stop, or carry on and save, does a rare error the app could not repair get a handler of its own, and does any handler swallow a failure, report success after one, or catch errors it was not written for? Sources: Hunt and Thomas, topic 24, Dead Programs Tell No Lies; Shore, Fail Fast (`reference/engineering/martin-fowler/fail_fast.md`); Ousterhout, chapter 10, Define Errors Out of Existence (10.7 Exception aggregation; 10.8 Just crash?).

## A write across two stores says how it ends halfway

**A change that writes to two stores or systems that no one transaction covers says how it ends if it stops between them: safe to run again, undone by a step that reverses the first write, or finished later by something that finds the half-done state.** A rule that spans two such writes holds only eventually, brought back within some time by a process named for it, so the process is part of the change and not left to hope that both writes succeed. A half-done state nobody comes back to is a wrong answer saved, the costliest kind, read back later as the truth. Within one store, one transaction holds both writes and none of this is needed. Check: does this change write to two places no one transaction covers, and if so, which of the three ends does it take, and what runs it? Source: Evans, chapter 6, The Lifecycle of a Domain Object (Aggregates: rules that span clusters are "resolved within some specified time"). Garcia-Molina and Salem, "Sagas" (1987), `reference/engineering/sagas/sagas.md`: section 1 (a long write split into steps, each with a compensating step that undoes it semantically, not by restoring the old values), 4 (backward recovery, undone by reversing steps), 5 (forward recovery, run again from a save-point until it finishes) and 7 (a daemon that finds sagas left half done and finishes them). Kleppmann and Riccomini, Designing Data-Intensive Applications, 2nd edition, `reference/engineering/kleppmann-ddia/`: chapter 1, Problems with Distributed Systems (a request that times out may or may not have been received, "and simply retrying it might not be safe"), and chapter 9, Faults and Partial Failures ("you may not even know whether something succeeded"), for why the halfway state happens; the book's chapters on transactions and on the ways to end it are not on the shelf, so the three ends are checked against "Sagas" only.
