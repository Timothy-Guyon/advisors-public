# Errors: what happens when it is wrong?

The claims about wrong input and wrong state, in the order they are tried: first make the error impossible; where it must exist, name the contract; when the contract breaks, stop there.

## Define errors out of existence

**Shape the interface so the error case cannot happen.** An error that is raised must be handled everywhere it can reach; an interface shaped so the case does not arise needs no handling at all, and where an error must exist, it is handled in one place. Each error a module raises is part of its interface and makes the module shallower, and one raised because the right behaviour was unclear passes the question to a caller who knows less. The usual move is to restate what the operation promises as a state to reach rather than a step to take, so the case that was an error becomes a call whose work is already done. An error that must exist is masked low, inside the module that meets it, where every caller would do the same about it, or aggregated high, left to rise to one handler near the top that reports the message written where the error was raised. An error is defined away or masked only where no caller needs to know of it; one a caller must act on stays in the interface. Check: can this error be defined out of existence at the edge where data enters, instead of handled at runtime, and if it must exist, is it masked in the module that meets it or left to one handler near the top rather than caught at each call, and is any error hidden that a caller needs? Source: Ousterhout, chapter 10, Define Errors Out of Existence (10.2 Too many exceptions; 10.3 Define errors out of existence; 10.5 Example: Java substring method; 10.6 Mask exceptions; 10.7 Exception aggregation; 10.10 Taking it too far).

## Say what it needs and promises

**A function says what it needs, what it promises and what stays true; what the types cannot state, a test states; and a promise that would surprise the people who know the domain marks a missing concept.** A caller that breaks the contract is told so loudly and early, a reader can tell from the interface what may be assumed, and the types carry as much of the contract as they can. A promise or an invariant is written in terms of states and never of steps, so its test is the setup, the call and the check, and an invariant is stated for a cluster as well as for a type. When the true promise of an operation is one a person of the domain would not guess, the fix is neither a comment beside it nor a change that alters its argument to make the arithmetic come out, but a model in which the promise is obvious. What an interface says includes every effect a later call can see that is not in its result, every error that can leave it, and every precondition that remains, the fewer the better. Check: does the required check pass (`CLAUDE.md` names it), does each new interface say what it needs and promises, is each promise the types cannot carry written as a test, and would any promise in this change surprise the people who know the domain? Sources: Hunt and Thomas, topic 23, Design by Contract; Evans, chapter 10, Supple Design (Intention-Revealing Interfaces; Assertions; Example: Back to Paint Mixing); Ousterhout, chapter 13, Comments Should Describe Things that Aren't Obvious from the Code (13.5 Interface documentation).

## Crash early

**A program that notices it is wrong stops there.** A crash near the cause beats a wrong answer far from it, and a wrong answer that gets saved is the costliest kind, because it is read back later as the truth. An error that is rare and that the app could do nothing useful about, its memory gone or its own state found inconsistent, gets no handler of its own and ends with a message that says what happened, unless recovering from it is part of what the app is for. Where a recovery from a large failure must exist anyway, a rare small error is promoted to that failure, so one recovery path serves both and runs often enough to be trusted; a frequent error is not, since each promotion pays the large recovery's cost. Check: when this code finds itself wrong, does it stop, or carry on and save, and does a rare error the app could not repair get a handler of its own? Sources: Hunt and Thomas, topic 24, Dead Programs Tell No Lies; Shore, Fail Fast (`reference/engineering/martin-fowler/fail_fast.md`); Ousterhout, chapter 10, Define Errors Out of Existence (10.7 Exception aggregation; 10.8 Just crash?).
