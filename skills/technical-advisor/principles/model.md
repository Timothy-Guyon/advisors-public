# The model: what kind of thing is it?

The claims about the kinds of thing in the domain, and about what is data rather than code.

## Entity or value

**A thing with an identity that lasts is an entity, and the model says what makes two of them the same one; a thing defined only by its values is a value object, immutable, or copied before it leaves its owner.** An entity stays the same thing while its attributes change, so it carries an identity: an identifier that matches the domain's own sense of sameness, never changes, and survives store and transfer. A place in memory or in a list is not an identity, the attributes used to find a thing, a name, a place, are ways to find it and not its identity, and where sameness cannot be settled by rule, the match is left to a person. A value object is its values and nothing more, and two with the same values are interchangeable; a mutable value handed out by reference can be altered by a caller and break its owner's rules, so a value is immutable and shared, or mutable and never shared, copied on the way out. Check: is each new thing in this change an entity or a value object; for each entity, what makes two the same, is that written in the type, and is the identifier fixed; and does any value go out mutable by reference? Source: Evans, chapter 5, A Model Expressed in Software (Entities, Designing the Identity Operation, Value Objects, Designing Value Objects).

## A value is a whole

**Attributes that mean something only together are one value object, and an entity holds what identifies and finds it.** Loose attributes on an entity that form a whole, as a street, a city and a code form one address, are gathered into one value with a name and its own rules; the entity is stripped to its identity, what finds it, and whole values, with other characteristics in things of their own. Things changed together are not one value for that alone: where callers still read and set each apart, joined they only hide one inside the other, and each is simpler as a value of its own. Check: does this change add a loose attribute to an entity that belongs with others as one value? Sources: Evans, chapter 5, A Model Expressed in Software, Modeling Entities, and Value Objects, the conceptual whole; Ousterhout, chapter 9, Better Together or Better Apart? (9.5 Example: insertion cursor and selection).

## Derived, not stored

**A thing that can be derived from what is already held is derived when asked, not stored beside it.** When a part's state can be rebuilt by a query over things held elsewhere, it needs no stored state of its own: it is worked out each time it is asked for, and the store holds one thing fewer to keep in step. Whether a root holds a collection of its parts or asks a query for them is a mechanism, chosen by how the thing is reached, and it changes nothing in the model. Check: does this change store what a query over things already held would give, and does a change of mechanism here leave the model as it was? Source: Evans, chapter 7, Using the Language: An Extended Example (Pause for Iteration: An Alternative Design of the Cargo Aggregate).

## Each change is an entry

**Where the domain must account for each change to an amount, the change is a new entry appended beside the others, never an edit or a removal, and the amount is derived from the entries.** An amount that is overwritten loses the change that made it; an entry kept keeps the whole history, a reversal is an entry of the opposite sign, and the amount is the combined effect of all entries, worked out when asked or cached behind the thing's interface, which is a mechanism and not a model choice. Whether the two sides of a move must balance is a further rigour the domain asks for or does not, and it holds only over a closed system that contains every source and sink. Check: does this change overwrite or delete a stored amount where the domain accounts for each change, or store a total that the entries would give? Source: Evans, chapter 11, Applying Analysis Patterns (Example: Earning Interest with Accounts; Accounting Models in Analysis Patterns).

## Every change through the log

**Where a log of changes is kept so that a thing's state can be rebuilt, event sourcing in Fowler's word, every change to that state goes through the log as an event, the state is derived from the log and held only as a cache of it, and the spec says which of the two, the log or the state, is the authority.** A log that most changes go through is a history and not an authority: one change made around it, an edit by hand or a fix applied to the state and not logged, leaves a state the log cannot rebuild and no reader can tell which; with every change an event, the state can be discarded and rebuilt from nothing, read as it stood at any event, and corrected by fixing what derives it and rebuilding, never by editing the state, and a reversal is a rebuild from an earlier point and needs no undo of its own. The state is held as data where the current state is what is asked for most, which is a mechanism; and since a change not logged cannot be recovered later, a thing that will want its history is logged from its first change. Check: does this change alter a logged thing's state without an event, fix a wrong state by editing it rather than by fixing what derives it and rebuilding, and does the spec say whether the log or the state is the authority? Source: Fowler, Event Sourcing.

## A question or a change, never both

**An operation either answers a question or changes state, never both; the answers are functions on values that return new values, and the changes are few and simple.** A function can be called at any time, called again, and combined with others without tracing what each one touched; an operation that computes and also alters forces every caller to take the alteration to get the answer. So a change on an entity returns no domain data and does as little as possible, the computation it needs is asked of a function first and handed in, and where the computation is involved it is a function on an immutable value that returns another value, so nothing that exists is altered, an argument least of all. Check: does any operation in this change both compute an answer and alter state, and could its computation be a function on a value instead? Source: Evans, chapter 10, Supple Design (Side-Effect-Free Functions; Separating Commands and Side-Effect-Free Functions; The Suppleness of the New Design).

## Closed where it fits

**Where it fits, an operation on a value takes and returns the value's own type, so the operations chain and the interface brings in no other concept; an operation closed on one side only, its argument or its return matching the receiver and the other a primitive or a basic library type, keeps most of the gain; and closure is sought on values, never forced on an entity.** An operation whose argument and result are the type that carries it is closed under that type, so a result can be the next argument and a sequence of them reads as one expression of the model, with nothing new to learn at the join; half-closed, with a number, a yes or no or a basic collection on the other side, it still frees the reader, since those add no concept. A value is where to look, because a new value can be conjured to answer a question, and a mutable whole is then replaced by a new whole rather than altered in place; an entity has a lifecycle the domain cares about, so one is not made to answer a question, though an operation on an entity may happen to return one of its kind. Check: for each operation on a value in this change, could its argument and its return be the value's own type, or one side a primitive, so that it chains with the others, does its interface bring in a concept the operation does not need, and is any entity here given a closed operation because the form was wanted rather than the thing? Source: Evans, chapter 10, Supple Design (Closure of Operations; Example: Collections; Example Integrating the Patterns: Shares Math, Share Pie Becomes a Value Object, Cascade of Insights, The Suppleness of the New Design).

## Aggregate

**A cluster that changes together has one root; outsiders hold only the root, other clusters are held by identity, the parts go when the root goes, and its invariants hold at every change inside the boundary and only eventually across it.** Outsiders go through the root and nothing reaches into the parts, so the rules that must always hold are checked in one place. A part's identity means something only inside its cluster, and it is reached by walking from the root, never by a find of its own; a reference the root hands out is used within one operation and not kept; a thing in one cluster that points at another cluster's root holds its identifier, not the object. The boundary is drawn by the domain: strict rules inside, where creation and deletion go together; loose ties across, where many clusters share a thing that changes at its own rate, and a fact needed as it was at the time is copied in as a value rather than looked up later. Check: does this change reach into a cluster's parts past its root, hold a reference into another cluster past its root, delete a root without its parts, or check a rule across clusters on every save? Source: Evans, chapter 6, The Lifecycle of a Domain Object (Aggregates, and Example: Purchase Order Integrity).

## Made whole or not at all

**A thing is made whole in one step with its rules met, or not at all; when making it is complex, the making is a job of its own.** A caller that assembles a thing piece by piece must know its insides and its rules, so those leak; a maker takes what is needed and returns the thing complete, or refuses, never a half-made one. A bare constructor is enough when making is simple and every attribute is at hand, and it keeps the same rule; a rule that can only be broken at making time lives with the maker, not carried by the thing for life. Check: is each new thing in this change made whole in one step with its rules met, and does any caller assemble parts it should not know? Source: Evans, chapter 6, The Lifecycle of a Domain Object, Factories, including When a constructor is all you need, and Where Does Invariant Logic Go.

## Brought back, not made again

**A stored thing brought back is the same thing in the middle of its life: it keeps its identity, and the rules of making a new one do not run again.** Rebuilding from the store takes the identifier as input and never mints one; a rule found broken in the store is a repair, not a refusal, since the thing already exists; and the caller is given the same thing, not a new one. Find-or-create is not offered, because whether a thing is new or existing matters in the domain. Check: does this change rebuild a stored thing by the path that makes a new one, mint an identifier on load, or offer find-or-create? Source: Evans, chapter 6, The Lifecycle of a Domain Object (Reconstitution of Stored Objects; Relationship with Factories).

## A copy stops at the boundary

**A copy of a root is a new thing of its cluster, decided part by part at the boundary: it takes a fresh identity from the source a new one would, starts each entity inside the boundary empty, copies the values, and points at the same roots outside the boundary rather than copying them.** A root is not copied by copying its bytes; each thing the boundary encloses is ruled on, and the boundary that says what a delete takes says what a copy takes too. An entity inside the boundary carries a history that belongs to the original, so the copy gets a new empty one; a value has no history, so it is copied or shared without difference; a root of another cluster is shared by many and lives on its own clock, so the copy holds the same identifier and the thing outside is left untouched, which is the opposite of a thing read back from the store, which keeps its identity because it is the same thing continued. The copy comes out whole, its identity and rules intact, from a maker that is a method on the original or a factory that takes it, never assembled by the caller. Check: does any copy in this change reuse the original's identity, carry over the history of an entity inside the boundary, copy a thing that sits outside the boundary instead of pointing at it, or alter anything outside the boundary, and is the copy made whole by one maker? Sources: Evans, chapter 6, The Lifecycle of a Domain Object (Aggregates; Factories; Reconstitution of Stored Objects); chapter 7, Using the Language: An Extended Example (Sample Application Feature: Repeat Business; Factories and Constructors for Cargo).

## Associations are constrained

**A relation between two things runs one way, is narrowed where the domain allows, and is cut if no scenario walks it.** A relation held on both sides means neither thing can be understood alone; the domain nearly always has a direction that matters, and the other is dropped. A relation narrowed to one per key writes a rule of the domain into the model, and a two-way relation between two value objects is a sign that one of them is an entity not yet recognised. Check: does each relation in this change run in one direction, is it as narrow as the domain allows, and does a scenario walk it? Source: Evans, chapter 5, A Model Expressed in Software, Associations.

## The slower thing knows nothing of the faster

**Where one thing of the model has meaning only against another that is meaningful standing alone, and the two change at different rates and for different reasons, the relation runs from the first to its backdrop and never back, and the backdrop carries nothing that exists for the sake of what stands against it.** Some domains stratify, what could be done, what is being done, what is to be decided, each stratum meaningful against the one below it and changing on a clock of its own; a reference or an attribute placed on the lower thing for the upper thing's purpose ties the slow thing to the fast one's reasons for change and hides a rule of the upper stratum in the lower. So the upper thing holds the reference, a find on the lower thing's door answers for the upper side where a scenario must walk the other way, and the attribute moves up into a named thing of the upper stratum; Evans names such strata responsibility layers, and they are named as such only under Order evolves. Check: for each relation or attribute this change adds, do the two things change at the same rate and for the same reasons, and if not, does the thing that stands alone now point at, or carry a field for, the thing that has meaning only against it? Source: Evans, chapter 16, Large-Scale Structure (Responsibility Layers; In Depth Example: Layering a Shipping System, the Route Bias Policy refactoring; Choosing Appropriate Layers, Conceptual dependency).

## The core's path is direct

**A thing of the core holds directly what its scenarios need, and a supporting thing the core's scenarios only pass through to reach it is taken off the path.** A walk that must first find the supporting thing by the role it plays, then ask it for what the core wants, clogs every story told about the model; held directly, attached when the core thing is made, the central scenarios are as short as they can be and the supporting thing can leave the core altogether, generic as it usually is. What is held directly is a reference or a value copied in at the making, never a derived total, and the tie that is bypassed stays on the supporting thing for its own scenarios. Check: does any core scenario in this change navigate through a supporting thing to reach what it needs, and could the core thing hold it directly? Source: Evans, chapter 15, Distillation (Segregated Core; Segregating the Core of a Cargo Shipping Model).

## Domain service

**An operation or a rule that belongs to no entity gets its own named place in the domain: named for the activity, stateless, speaking in the model's things, and readable by the people who know it; a process is one only when the people who know the domain talk about it.** Some operations take domain things and answer, and own no state; such an operation is a named service in the domain, not a method on whichever object was nearest, and the model holds behaviour, not only data shapes. The name is a verb from the glossary or a candidate for it; the service holds no state of its own, so any caller may use it without regard to history; what it takes and returns are the model's things, not strings and identifiers; it is used sparingly, so entities keep their behaviour and no doer called a manager accretes, and one that only orders a task, with no rule of the domain in it, belongs with the task, not in the domain. A rule written as a guard inside a larger operation cannot be found or checked by the people who know the domain; given a name and a place of its own, it can be read against the line that states it. The test for a process is whether the people who know the domain talk about it: one they talk about is made explicit as such a place, one with more than one way becomes a choice between named ways, each a strategy in Evans's word, that a caller picks, and one they never mention is mechanism and stays hidden. Check: is each operation or rule in this change on the thing it belongs to, or in a named place of its own, named for an activity, stateless and speaking in the model's things, that the people who know the domain can read, does any object hold only data while its behaviour sits elsewhere, and where a process has more than one way, is each way a strategy a caller chooses, and is any process here one the people who know the domain never mention? Sources: Evans, chapter 5, A Model Expressed in Software (Services, and Services and the Isolated Domain Layer); chapter 1, Crunching Knowledge, Example: Extracting a Hidden Concept; chapter 9, Making Implicit Concepts Explicit (Representing Processes as Domain Objects); Fowler, Anemic Domain Model.

## The way is handed in, never branched on

**A process that can be done more than one way is written once and runs the same whatever the way, and the way is a strategy, one named thing of the model handed to the process, with the one question the process asks of it as its whole interface.** The sign of the missing strategy is the same condition tested in computation after computation, the choice smeared through the process so that neither the process nor the choice can be read, and a new way touching every branch. Separated, the stable part can be said in one sentence of the domain's words and the varying part is a named strategy the people who know the domain recognise, and a new way is a new strategy and nothing else. The strategy's interface is cut to the single answer the process needs from it, a number, a yes or no, a rank, and a strategy holds no state, so one may be shared by every caller. Check: does any branch on which way appear inside the process in this change rather than in one strategy handed to it, is the strategy's interface the one question the process asks, and can the process then be said in one sentence? Source: Evans, chapter 12, Relating Design Patterns to the Model (Strategy, also called Policy; Example: Route-Finding Policies).

## Specification is a value

**A yes-or-no rule about a thing that does not fit on the thing is a value of the model that tests the thing, and the one test serves to check, to select and to build to order.** A test that grows past a line swells its host with branches; moved to a task or a screen, it leaves the model unable to say its own rule. As a value it is named for the rule, carries what it needs to judge, and is written once, so the check at a save, the filter over a list and the request to a maker cannot drift into three forms. Two such values combine by and, or and not into a value that is again a rule, so a rule made of others is written as their combination and never as a fresh branch; and whether every thing one rule admits a second admits too, subsumption in Evans's word, is asked of the two rules as values, never by running both over the things. Check: does this change write a yes-or-no rule of the domain as a branch in a screen, a task or a query, where one named test of the model could serve to check, select and make, and is a rule built from others, or compared with another, handled as values rather than as branches or runs? Sources: Evans, chapter 9, Making Implicit Concepts Explicit (Specification; Applying and Implementing Specification); chapter 10, Supple Design (Extending Specifications in a Declarative Style, Combining Specifications Using Logical Operators and Subsumption).

## A constraint has a name

**A rule that keeps a thing within bounds is a named method on the thing, and becomes a thing of its own when it needs data the host does not hold, when kin rules appear on things that are not a family, or when it is talked about more than it is seen in code.** Inline, a bound hides inside the operation that changes the state, and no one can read it or check it against the line that states it; named, it reads against that line. The three signs say the rule has outgrown its host and is a concept of the model with a name and a place of its own. Check: is each constraint in this change a named method on its host, and does any show one of the three signs? Source: Evans, chapter 9, Making Implicit Concepts Explicit (Explicit Constraints; Review Example: Overbooking Policy).

## The rule's owner derives

**A value derived from a thing's data belongs to the thing that knows the rule, not the thing that holds the data.** The same data can be cut one way for one purpose and another way for another, and the rules for a cut change on their own; deriving the value on the thing that holds the data loads it with every purpose's rules and ties it to concerns outside its own. So the derivation sits with the service or the thing that owns the rule, which reads the data it needs from the thing that holds it. Check: for each derived value in this change, could another purpose derive it differently, and if so does the owner of the rule derive it rather than the owner of the data? Source: Evans, chapter 7, Using the Language: An Extended Example (New Feature: Allocation Checking, the final design question).

## A reacting rule has one trigger

**A rule that derives a new thing from new data has one defined point of initiation and one owner of finding what is new: fired at once by each change, fired by the holder of the data when told, or fired by the rule itself when told, reading what arrived since it last ran.** At once is the obvious choice and often the worst: it ties the rule to whoever makes the change and to that moment. Deferred, the holder or the rule keeps a mark of its last run and finds what is new. Different rules may fire differently, but one rule fires one way, and the way is said in the spec, since the timing and control of such updates is where dependencies tangle. Check: for each rule in this change that reacts to new data, who starts it, who finds what is new, and is that one way, named? Source: Evans, chapter 11, Applying Analysis Patterns (Continuing Example: Insight into the Nightly Batch; Posting Rules; Executing Posting Rules).

## Facts are data

**What the domain says is data, written by its own method, and code holds no copy of it.** A fact about the domain is data, not a line of code: it is written where its kind of fact is written, by the method that checks it, and code reads it. Check: does this change put a fact about the domain into code? Sources: the founder's rule, 2026-10-13; Hunt and Thomas, topic 14, Domain Languages.

## Knowledge level

**Where one part of the model describes what another part may be, its kinds, the values it may take and the relations it may hold, that part is a knowledge level, in Evans's word: a distinct set of ordinary types of the model, kept apart from the things it describes, which point at their kind in it, and cut to the constraints the domain has settled rather than to a general framework.** The things of the operational level, made and changed every day, each point at their kind in the knowledge level and are constrained by it, so a rule about what a thing may be is a thing of the knowledge level and never a field or a branch on the thing it governs; an attribute read one way in one situation and another way in another is the sign of a kind the knowledge level is missing. The two levels depend on each other both ways, which makes this a level and not a layer, and its types are ordinary types of the domain part, never the language's own reflection. It is reached for only where the describing part is truly changed between runs, by the people who know the domain or by a user and not by a change to the code, and would otherwise distort the operational things into jacks-of-all-trades, since every option added to it is one more the person who configures it must understand and one more place a mistake misbehaves everywhere. Check: does this change add a kind, a value or a relation that says what another thing may be, is it a thing of the knowledge level rather than a field or a branch on the thing it governs, is that level built of ordinary types and no wider than the constraints settled, and is any attribute here read differently from one situation to the next? Source: Evans, chapter 16, Large-Scale Structure (Knowledge Level; Example Part 1: Employee Payroll and Pension; Example Continued: Payroll and Pension Knowledge Level).

## A change to the knowledge level reaches what it describes

**A change to the knowledge level, a kind added or removed, a value renamed, a relation narrowed, says what becomes of every operational thing already made under the old description: carried as it is, rewritten under the new, or kept beside the new as a thing of the old kind.** The things made under the old description do not change with it, and left unaddressed they are read back under rules they were never checked against, which is a wrong answer saved as the truth. So the spec of such a change names the operational things the change reaches and chooses one of the three for each, and old and new coexist only where the model can say which description a thing was made under. Check: does this change alter a thing that describes what other things may be, and if so, does its spec say, for each kind of thing already made under the old description, whether it is carried, rewritten or kept as it was? Source: Evans, chapter 16, Large-Scale Structure (Knowledge Level, the cautions after the pattern statement).

## Rules are written over the things they govern

**A rule held apart from the things it governs, as data, as a compiled file or in an engine of its own, is written over those things' own model, their attributes, their values and their names, and never over a model of its own; a form of its own for rules is a form, not a second context.** Rules written over a different model than the things they apply to force one of two failures: the cost of keeping the two in step climbs, or the things are dumbed down to whatever the rule form can read, a bag of strings with no behaviour. The form the rules take may differ from the form the things take, and that difference is machinery; what the rules say is said in the one model, so a rule can be read against the thing it governs without translation, and a change to a thing's attributes is a change to its rules by the same word. Check: does any rule in this change name an attribute, a value or a thing in words or a form other than the model's own, and is any thing here flattened so that a rule form can read it? Source: Evans, chapter 16, Large-Scale Structure (Choosing Appropriate Layers, the Policy layer and rules engines).

## One model

**There is one model, and the code holds it literally; a model that will not go into code naturally is changed, never mapped.** A model kept for understanding and a design kept for code drift apart, and what is learned in one never reaches the other; so each type in the domain part is one thing of the model, the mapping obvious enough to need no table. Where the model proves awkward to implement, or the code proves unfaithful to the domain, a new model is sought that serves both, rather than a translation between them. Check: is each type in this change one thing of the model with no mapping between, and where the model would not go in naturally, was the model changed? Source: Evans, chapter 3, Binding Model and Implementation, Model-Driven Design.

## Code change is model change

**A change to the domain part of the code changes the model, and is named as one.** A refactor there that moves an attribute, a relation or a rule is not a tidy but a model change: its spec and its commit say so, and the glossary follows it, or it does not happen. A refactor made without knowing this weakens the model while leaving the code working. Check: does this change move a thing, a relation or a rule of the model, and if so, is it named as a model change rather than a cleanup? Source: Evans, chapter 3, Binding Model and Implementation, Hands-On Modelers.

## Explicit, not inferred

**What the code works out from a name, a prefix or an order is a thing of the model, and the working-out happens once, where the data comes in.** Code that infers a concept from the shape of names or the order of a file holds the concept nowhere, so it cannot be tested alone and dies with the file format. The concept becomes a thing in the model; the rule that recognises it lives in one place at the edge where data enters; the thing itself knows nothing of how it was recognised. Check: does this change infer a concept by matching, sorting or naming where a thing could hold it, and does any thing depend on how it was found? Source: Evans, chapter 3, Binding Model and Implementation, Example: From Procedural to Model-Driven.

## Nothing stands in for an unsettled rule

**Where the domain has not settled a rule, the code holds nothing in its place.** The people who know the domain carry rules that contradict each other and fill the gaps by feel; code cannot. A rule is settled before it is coded, and where it is not, the change names the gap as out of scope rather than shipping a default or a branch that guesses. Check: does any default or branch in this change stand in for a rule the founder has not settled, and is the gap named? Source: Evans, chapter 1, Crunching Knowledge, Knowledge Rich Design.

## Walk the scenario

**A change is said aloud and walked as a scenario in the model's words before it is coded; a sentence that will not come out plain, or a scenario the model cannot carry, changes the model.** The scenario is spoken as sentences of the model's things and their relations, and each step names which thing holds the knowledge and which passes it on. A sentence that comes out as attributes and the steps done to them marks a thing the model lacks: it is named, as a glossary candidate if the glossary lacks it, and the code holds it as one thing rather than a function over loose attributes. Where the walk falls through, the model gains or recasts a concept; the change is never patched beside the model, in a screen or a handler. Check: can this change's scenario be said in one plain sentence of the model's words, which things of the model carry it end to end, and where does it fall through? Sources: Evans, chapter 1, Crunching Knowledge, the scenario walks and Deep Models; chapter 2, Communication and the Use of Language, Modeling Out Loud and Example Dialogs.

## A contradiction marks a concept

**Two statements by the people who know the domain that both seem true and contradict are not settled by picking one; the model looks for the thing under which both hold.** Some contradictions are only words or a misreading, and clearing those is enough; what remains is a lead to a concept the model is missing, and the thing found often carries the next scenario too. Check: does this change settle a contradiction by picking a side where a thing of the model could carry both? Source: Evans, chapter 9, Making Implicit Concepts Explicit (Contemplate Contradictions).

## A clash marks two models

**When a second use of a thing arrives and the thing's interface does not fit it, or its behaviour surprises, the cause is two models combined without anyone noticing, a duplicate concept or a false cognate, and the fix is to find both models and unify them or draw a border between them, never to add the second use's field to the first's type.** A duplicate concept is two things that are one and are kept apart; a false cognate is one word on two things that look the same and are not, so that each side's rules hold in its own context and break in the other's once the type is shared. A type widened to serve a second context carries both sets of assumptions and is reliable in neither; unified, the one thing holds under one set of rules, and bordered, each keeps its own with the translation at the line. Check: does this change widen an existing thing for a new use, and if so, is the new use the same concept under the same rules, or a second model that wants a border? Source: Evans, chapter 14, Maintaining Model Integrity (the opening example; Bounded Context, Recognizing Splinters Within a Bounded Context).

## The domain's book

**Where the domain has a literature, its settled concepts are the first candidates for a missing thing, cut to what the scenario needs and never pasted whole.** A field with thinkers has already named its things and their relations; starting there gives a coherent model to test with the people who know the domain, instead of a concept invented from scratch. What comes in is cut to the scenario at hand, and a concept the literature holds that no scenario reaches stays on the shelf. Check: before this change names a new concept, was the domain's own literature read for one, and is what came in cut to the scenario? Source: Evans, chapter 9, Making Implicit Concepts Explicit (Read the Book; Example: Earning Interest Revisited).

## A pattern in the model says something of the domain

**A pattern from the programming books gets a name in the model only when the people who know the domain would recognise the thing it names; otherwise it is plumbing, kept behind a door and named nowhere in the model.** A pattern carries two levels, the shape in the code and the concept in the model, and a domain pattern holds on both: a strategy, a whole made of parts of its own kind, are things the people who know the domain would recognise. A pattern that holds on the code level only, a shared instance, a cache, a pool, is an implementation choice that changes the model not at all, and it is not written into a type's name or its place; a caller sees the same door whether or not it is there. Where a pattern fits on both levels, its known consequences and ways of building apply in full and are used rather than rediscovered. Check: for each pattern this change reaches for, would the people who know the domain recognise the thing it shapes, and if not, is it kept behind a door with no word of it in the model? Source: Evans, chapter 12, Relating Design Patterns to the Model (the opening; Why Not Flyweight?; the closing paragraph).

## The model is distilled

**A concept no scenario reaches is dropped, and a needed concept tied to an unneeded one is cut free.** The model holds what its scenarios touch, and nothing kept against the day it might matter. Where a needed concept cannot be stated without one that is not, the model is recut until the needed one stands alone, and a thing's full behaviour gives way to the simplification the scenario needs. The same cut runs over the model as a whole: the concepts distinctive to what the app does for its users are brought into relief as its core domain, in Evans's word, and the concepts any app of the kind would hold are boiled off into parts of their own, so the core stays small. Check: which concept in this change does no scenario reach, and can it go without taking a needed one with it? Sources: Evans, chapter 1, Crunching Knowledge, Why It Worked, distilling the model; chapter 15, Distillation (Core Domain).

## Special cases are one concept

**Two things that are special cases of one idea become that idea, named in the words of the people who know the domain, and their special-case code goes.** A pair of types doing the same job for two owners, each with its own arithmetic and its own corrections, hide a general concept with a rule of its own; made explicit, the arithmetic is written once and composes, the corrections vanish, and the inconsistencies rooted in the split go with them. A name the people who know the domain do not use, kept because it seemed useful to the code, is the first thing to suspect. Check: do two things in this change do the same job for two owners, and is any name here one the people who know the domain would not say? Source: Evans, chapter 8, Breakthrough (A Deeper Model).

## The normal case covers the special one

**A special case is designed out of existence by shaping the normal case so it covers the special one with no code of its own.** Each special case is a branch every reader follows and every change must remember, so a state that seems to need a flag, none chosen or nothing yet, is held as the ordinary value at its empty end, an empty range or an empty list, on which the normal operations already do the right thing, even where a screen shows the case as different. Where the absence is itself a fact a caller needs, it is not a special case to design away, and it keeps a form of its own. Check: does this change add a flag, an optional or a branch for a case the ordinary value could carry at its empty end, and do the normal operations then run on it with no check? Source: Ousterhout, chapter 10, Define Errors Out of Existence (10.9 Design special cases out of existence; 10.10 Taking it too far).

## Parts of the same kind are one type

**A whole whose parts are things of its own kind is one type at every level, which answers the same questions at every level, a container from its parts and a leaf from its own values, and a caller never asks which it holds.** This holds only where the people who know the domain truly call every level the same kind of thing; a convenient recursion over things they tell apart is not it, and a level they name is kept as a level, not flattened into a string of parts. Where it holds, the questions a caller asks are answered by the one type, the container by combining its parts' answers and the leaf from itself, so no behaviour is written once per level; a part that differs from the others in how it is made is still the one type to its callers. It is reached for when a nesting of this kind arrives, not kept ready for one. Check: does this change hold a whole and its parts of the same kind as separate types, or walk them through different interfaces, where one type could answer the same questions at every level, and does the domain truly call every level the same kind? Source: Evans, chapter 12, Relating Design Patterns to the Model (Composite; Example: Shipment Routes Made of Routes).
